# Coding agent

Это учебный консольный агент на Python. Он получает задачу, сам выбирает инструменты, читает и меняет файлы и запускает тесты

В проекте реализованы все части задания до 10 баллов:

- agent loop и tool calling
- режимы `safe` и `auto`
- правила безопасности в `policy.json`
- сохранение состояния по `run_id`
- Plan Mode
- лимиты запросов и действий
- задачи с зависимостями
- просмотр diff и безопасный откат

## Установка

Нужны Python 3.11+, Bash и Ollama

Перейти в папку проекта:

```bash
cd ~/PycharmProjects/coding_agent
```

Проект работает без дополнительных библиотек. При желании его можно установить как пакет:

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -e .
```

## Запуск Ollama

Загрузить модель:

```bash
ollama pull qwen3:4b
```

Проверить, что Ollama работает:

```bash
ollama list
```

Если сервис остановлен:

```bash
sudo systemctl start ollama
```

Перед запуском агента нужно задать настройки в том же терминале:

```bash
export OPENAI_BASE_URL=http://localhost:11434/v1
export OPENAI_API_KEY=ollama
export OPENAI_MODEL=qwen3:4b
export OPENAI_TIMEOUT_SECONDS=600
```

Пример этих настроек также находится в `.env.example`

## Быстрая проверка

Запустить все тесты проекта:

```bash
python3 -B -W error::ResourceWarning -m unittest discover -s tests -q
```

Последний результат:

```text
Ran 59 tests in 3.824s
OK
```

Запустить готовую демонстрацию:

```bash
python3 -B -m coding_agent.demo
```

Демо создаёт отдельную копию контрольного проекта, исправляет `order.py`, запускает два теста, показывает diff и делает rollback. Исходная папка `workspace` не меняется

## Основной запуск агента

Пример задачи из условия:

```bash
python3 -m coding_agent run \
  --workspace ./workspace \
  --policy ./policy.json \
  --mode safe \
  --plan \
  --prompt 'Исправь расчёт итоговой стоимости заказа, чтобы тесты проходили. Тесты не меняй. Сам найди нужные файлы, внеси исправление и запусти тесты.'
```

После запуска программа покажет `run_id`. Его нужно подставлять в следующие команды вместо `RUN_ID`

## Работа с планом

Посмотреть сохранённое состояние:

```bash
python3 -m coding_agent status RUN_ID
```

Утвердить план и продолжить:

```bash
python3 -m coding_agent plan approve RUN_ID
python3 -m coding_agent resume RUN_ID
```

Отклонить план:

```bash
python3 -m coding_agent plan reject RUN_ID
python3 -m coding_agent resume RUN_ID
```

До утверждения плана агент может только смотреть список файлов и читать их. Изменять файлы и запускать Bash в этот момент нельзя

## Подтверждение действий

В режиме `safe` запись и Bash ждут подтверждения. Когда программа остановится, она покажет `CALL_ID`

Разрешить действие:

```bash
python3 -m coding_agent action approve RUN_ID CALL_ID
python3 -m coding_agent resume RUN_ID
```

Отклонить действие:

```bash
python3 -m coding_agent action reject RUN_ID CALL_ID
python3 -m coding_agent resume RUN_ID
```

В режиме `auto` разрешённые запись и Bash выполняются сразу. Удаление файла всегда требует подтверждения

## Инструменты

У агента есть пять инструментов:

- `list_files` — показать файлы
- `read_file` — прочитать файл
- `write_file` — записать файл
- `delete_file` — удалить файл
- `Bash` — запустить разрешённую команду

Модель только предлагает действие. Перед выполнением программа проверяет название инструмента, аргументы, путь и правила безопасности

## Policy

Правила находятся в `policy.json`. В нём указаны:

- разрешённые команды
- запрещённые команды
- разрешённые папки
- запрещённые папки
- защищённые файлы
- лимиты запуска

Запрет имеет больший приоритет, чем разрешение. Агент не может выйти за пределы workspace через абсолютный путь, `..` или симлинк. Файл `test_order.py` защищён от изменения

Bash выполняет только команды, которые явно разрешены в policy. Конвейеры, перенаправления, `bash -c` и `python -c` блокируются

## Задачи

После утверждения плана его шаги становятся задачами. Следующая задача запускается только после выполнения зависимостей. Одного сообщения модели недостаточно: нужен настоящий результат инструмента

Посмотреть задачи:

```bash
python3 -m coding_agent tasks RUN_ID
```

В контрольном примере используются три задачи: прочитать файл, исправить его и запустить тесты

## Восстановление после остановки

Состояние хранится в SQLite. Обычный остановленный запуск можно продолжить:

```bash
python3 -m coding_agent resume RUN_ID
```

Уже завершённое действие повторно не запускается

Если программа остановилась прямо во время действия, сначала нужно посмотреть его состояние:

```bash
python3 -m coding_agent recover show RUN_ID CALL_ID
```

Повторить безопасное действие:

```bash
python3 -m coding_agent recover retry RUN_ID CALL_ID --changes accept
```

Считать действие неуспешным и продолжить:

```bash
python3 -m coding_agent recover fail RUN_ID CALL_ID --changes accept
```

Завершить запуск:

```bash
python3 -m coding_agent recover abort RUN_ID CALL_ID --changes exclude
```

Bash и удаление автоматически не повторяются, потому что у них могут быть побочные эффекты

## Лимиты

Для каждого `run_id` ограничиваются:

- количество запросов к модели
- количество вызовов инструментов
- количество действий с побочным эффектом
- общий размер результатов инструментов

После `resume` лимиты не обнуляются. Если места для всей пачки действий не хватает, она не выполняется

## Diff и откат

Посмотреть изменения конкретного запуска:

```bash
python3 -m coding_agent diff RUN_ID
```

Вернуть изменённые агентом файлы:

```bash
python3 -m coding_agent rollback RUN_ID
```

Перед откатом программа проверяет файлы. Если пользователь изменил один из них после агента, rollback остановится и ничего не перезапишет

## Что было проверено

Автоматические тесты проверяют инструменты, режимы `safe` и `auto`, policy, защиту путей, Plan Mode, восстановление после сбоя, лимиты, задачи и rollback

В демонстрации агент прочитал `order.py`, исправил расчёт скидки и запустил `python3 -m unittest -v`. Оба теста прошли, а `test_order.py` не изменился

Для работы использовалась локальная Ollama с моделью `qwen3:4b`. Она смогла составить правильный план. На моём компьютере полное выполнение работало медленно, потому что модель запускалась на CPU
